# AI Entry-Level Curriculum — 50-Minute Talk Checklists

This repository turns real university computer science curricula into checklists of standalone 50-minute talks — one talk per topic, sized so a competent speaker could fill the slot without overrunning, derived only from what each source actually states (never invented).

![Bob and AI Teaching the Backbone Curriculum](./images/cs-in-ai-008.jpg)

## The Backbone Curriculum

Line up all seven schools and the same ~25 subjects show up again and again under different course numbers. This section names those subjects once — the **backbone** — and gives each one a real talk outline in `talks/`: a one-sentence pitch, a time-boxed segment table that sums to exactly 50 minutes, and enough per-segment content that someone could walk in and give the talk from the outline alone.

Building those outlines surfaced a second layer: eleven commonly-cited "top algorithms in computer science" categories (sorting/searching, graph routing, cryptography, compression, ML/web-ranking) that a broad backbone talk either couldn't fit or didn't name. Five of those needed a **dedicated talk of their own** — a single 50-minute "Algorithms" session cannot do Dijkstra's, BFS, DFS, binary search, quicksort, mergesort, *and* PageRank justice — so they're numbered `28`–`32` and slotted into the table below right next to the backbone subject they extend, rather than tacked onto the end as an afterthought. The other six algorithms had room to go deep *inside* an existing talk and are marked inline where that happened.

The table is the single index for both layers — 27 backbone subjects plus 5 algorithm deep-dives, 32 talks total. It's not a re-derivation of the ~3,300 talk titles already in `curriculum/` (see the bottom of this file) — it's the outline layer on top of them, cross-referenced against where each subject lives in the school files and, where one exists, a free MIT OpenCourseWare or Harvard Professional & Lifelong Learning (PLL) companion course.

## Canonical Algorithms Audit — Methodology

Every school file in `curriculum/` was checked for thirteen specific algorithms across those eleven categories. Six turned up already in the raw curriculum data; five were named nowhere in any of the seven schools. That was the first test — *does the data already mention this algorithm?*

Building `talks/` required a second, independent test: *does it fit inside an existing 50-minute talk, or does it need one of its own?* The two tests didn't always agree — BFS/DFS, binary search, and the FFT had all already turned up somewhere in a school's checklist, but still earned a dedicated talk (rows 28-31 above) because there wasn't room to do them justice alongside everything else "Algorithms" or "Information Theory" needed to cover. Both outcomes are marked directly in the table above; nothing here repeats it.

## Backbone Priorities for AI-Assisted Software Development

As AI systems take on more of the code-writing itself, the developer's job shifts from "produce the code" to "specify the right thing, verify what came back, and own the judgment calls AI can't make for itself." That reframes which of the 32 talks in this repo (27 backbone + 5 algorithm deep-dives) matter most going forward. This is a judgment call, not a formula — but it's made against one consistent test:

> **If a developer is weak on this subject, does leaning on AI make that weakness *dangerous* — producing confident, wrong, hard-to-catch output — or does it just make them *less deep*, with AI genuinely covering the gap?**

### Critical — AI makes weakness here dangerous, not just shallow

| # | Talk | Why it stays critical |
|---|---|---|
| 1 | [Introduction to Programming](talks/01-introduction-to-programming.md) | Someone still has to read, direct, and verify the code; the literacy layer doesn't disappear because AI drafts the first version. |
| 2 | [Data Structures](talks/02-data-structures.md) | Catching an AI's inefficient structure choice (a linear scan where a hash lookup belongs) requires knowing the tradeoffs yourself. |
| 3 | [Algorithms](talks/03-algorithms.md) | Recognizing an AI-generated O(n²) solution to an O(n log n) problem requires knowing what "should" be possible in the first place. |
| 4 | [Discrete Mathematics for CS](talks/04-discrete-mathematics-for-cs.md) | Precise, formal reasoning is exactly the skill needed to write specifications AI can't misread and to verify its logical claims are actually sound. |
| 7 | [Introduction to Computer Systems](talks/07-introduction-to-computer-systems.md) | Memory and concurrency bugs are exactly where AI-generated code fails silently; without this, you can't even see that the bug exists. |
| 11 | [Database Systems](talks/11-database-systems.md) | Schema and query mistakes compound silently over time; AI-assisted applications live or die on the data layer being right. |
| 14 | [Software Engineering](talks/14-software-engineering.md) | Process, testing, and review discipline get *more* important as AI writes more code faster — this becomes the human's actual job. |
| 15 | [Computer & Network Security](talks/15-computer-and-network-security.md) | AI-generated code has well-documented, repeatable security blind spots; someone has to be the one who catches them before shipping. |
| 17 | [Artificial Intelligence](talks/17-artificial-intelligence.md) | Understanding search, planning, and reasoning is understanding how the tools you now work with every day actually behave. |
| 18 | [Machine Learning](talks/18-machine-learning.md) | You're increasingly shipping software that wraps or depends on ML systems; you need to understand training, generalization, and failure modes to trust them appropriately. |
| 20 | [Natural Language Processing](talks/20-natural-language-processing.md) | You interact with AI in natural language constantly; understanding how it's processed — and where it hallucinates — is directly, continuously applicable. |
| 23 | [Human-Computer Interaction](talks/23-human-computer-interaction.md) | As AI absorbs more implementation work, deciding *what's actually worth building for humans* becomes the differentiating skill left to people. |

## Notes on Scope

- **"Backbone" is a curated set, not a formula.** 24-28 was the target size; 27 landed as the number of subjects that were both (a) common across at least three of the seven schools and (b) distinct enough to deserve their own line rather than folding into a neighbor (e.g., Deep Learning is split from Machine Learning because enough schools — MIT, CMU — treat it as its own course).
- **MIT OCW links** point to the syllabus page already cited in `curriculum/mit-ocw-cs-curriculum-talks-checklist.md` — no new fetching was needed since that file already curated the best OCW match per subject.
- **Harvard PLL** (`pll.harvard.edu/catalog/free`) is a different catalog than the SEAS academic listing used to build `curriculum/harvard-cs-curriculum-talks-checklist.md` — it's Harvard's free/open online course catalog (mostly CS50 spinoffs and the *Data Science* edX series). Only 8 of its 127 free listings matched a backbone subject; the rest (world literature, Chinese history, neuroscience, biochemistry, etc.) aren't CS and were left out.
- Six of the 27 backbone rows (Deep Learning, Computer Vision, Robotics, Parallel Computing, Information Theory, and to a lesser extent Distributed Systems) have no Harvard PLL match at all — Harvard's *free* catalog just doesn't reach that deep into the specialized graduate curriculum the way MIT OCW does.
